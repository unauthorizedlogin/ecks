# 🔑 Save Key Provider

### Purpose

`SaveKeyProvider` owns the encryption and authentication keys required by `SaveSecurity`. It provides a local key-storage implementation while keeping key acquisition abstract enough for future secure providers.

### Architecture Role

```text
SaveSecurity
    ↓
SaveKeyProvider
├── Encryption Key
└── Authentication Key
        ↓
Local Key Storage
user://security/save_keys.dat
```

`SaveKeyProvider` is a `RefCounted` service responsible for key generation, loading, storage, and access.

### Responsibilities

* Generate cryptographically random save keys.
* Maintain separate encryption and authentication keys.
* Persist keys locally.
* Load previously generated keys.
* Validate stored key data.
* Expose keys to `SaveSecurity`.
* Provide an abstraction point for alternate key providers.

### Key Structure

A total of **64 bytes** is generated and divided into two independent 32-byte keys:

```text
64-byte random key material
        ↓
├── 32-byte Encryption Key
└── 32-byte Authentication Key
```

The encryption and authentication keys are exposed separately through:

* `get_encryption_key()`
* `get_authentication_key()`

### Initialization Flow

```text
load_or_create_keys()
        ↓
   Key file exists?
      ↙       ↘
    YES        NO
     ↓          ↓
_load_keys()  _generate_keys()
                 ↓
             _save_keys()
```

Existing keys are reused rather than regenerated, ensuring previously encrypted saves remain accessible.

### Key Generation

`_generate_keys()` uses Godot's `Crypto.generate_random_bytes()` to generate the complete key material.

The generated bytes are split into the encryption and authentication keys before being persisted.

### Key Storage

Keys are stored at:

```text
user://security/save_keys.dat
```

The provider creates the `security` directory when necessary and writes both keys sequentially into the file.

### Key Validation

When loading, the provider requires exactly `TOTAL_KEY_SIZE` bytes.

Invalid or truncated key files return `ERR_FILE_CORRUPT` rather than producing partially initialized security keys.

### Provider Abstraction

The local implementation is intentionally isolated behind `SaveKeyProvider`, allowing future implementations to source keys from:

* Server infrastructure
* Cloud services
* Platform credential storage
* Other secure key providers

`SaveSecurity` therefore depends on the **key provider interface**, rather than directly owning key-generation or storage logic.

### File(s) Affected

* `save_key_provider.gd`
* `SaveSecurity`
* `SaveManager`

### Notes

`SaveKeyProvider` is the **key-management boundary** of the save security system.

It owns key lifecycle and access, while `SaveSecurity` owns cryptographic processing and `SaveManager` owns save persistence.
